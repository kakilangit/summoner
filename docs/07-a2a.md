# A2A (Agent-to-Agent)

Summoner implements the [A2A protocol](https://github.com/google/A2A) for inter-agent communication. This enables agents running on different platforms to exchange messages, delegate tasks, and collaborate.

## Concepts

| Term | Role | Description |
|------|------|-------------|
| **Herald** | A2A Server | Exposes local agents to external A2A clients |
| **Envoy** | Remote Agent | Outbound connection to an external A2A agent |
| **Ward** | A2A Token | Bearer token for authenticating with a Herald |

## Herald (A2A Server)

A Herald is a workspace-scoped A2A server endpoint. It accepts inbound `message/send` requests and routes them to local agents.

**Create a Herald:**

1. Navigate to **Heralds** in a realm
2. Click **New Herald**
3. Configure:
   - **Name**: Display name
   - **Access mode**: `public` (no auth) or `token` (requires a Ward)
   - **Linked agents**: Which local agents are exposed via this endpoint

**Wards (Tokens):**

For token-gated Heralds, create Wards to issue bearer tokens:

1. From the Herald detail page, navigate to **Wards**
2. Click **New Ward**
3. Set a label and optional expiration

Clients authenticate with `Authorization: Bearer <ward_token>`.

**Agent Card:**

Each Herald auto-generates an [Agent Card](https://github.com/google/A2A/blob/main/specification/json/README.md) at `/.well-known/agent.json` (or a custom path). The card advertises the agent's name, description, capabilities, and skills.

## Envoy (Remote Agent)

An Envoy is a remote agent registered via its agent card URL. Summoner fetches and caches the agent card for discovery, capabilities, and skill metadata.

**Create an Envoy:**

1. Navigate to **Summons**
2. Click **New Summon** and select **Remote** type
3. Enter the agent card URL (e.g. `https://example.com/.well-known/agent.json`)
4. Configure authentication:
   - **None**: No auth headers
   - **Bearer token**: Links a Seal for `Authorization: Bearer` header
   - **API key**: Links a Seal for `X-API-Key` header
5. Set a timeout (default 30s)

The agent card is fetched on creation and refreshed periodically.

## Skill Routing

The A2A spec defines skills as discovery metadata on agent cards. Summoner uses skills to route requests to the correct capability on multi-skill remote agents.

**How it works:**

1. The remote agent's cached agent card contains a `skills` list with `id`, `name`, `description`, `tags`, and `examples`
2. When sending a message, Summoner resolves the skill:
   - **Explicit**: Pipeline stages can specify a `skill` field targeting a specific skill ID
   - **Inferred**: For conversations and swarms, `SkillResolver` matches the user message against skill metadata using keyword matching
3. The resolved skill is sent as a `DataPart` alongside the `TextPart` in the A2A message

**Resolution precedence:** explicit skill (from pipeline stage) > inferred skill (from agent card matching) > no skill (free-form text).

## Remote Agents in Workflows

Remote agents participate in pipelines and swarms alongside local agents, with constraints enforced at creation time.

### Pipelines (Quests)

- **Simple mode**: Remote agents work as stages. Each stage receives the previous output as an A2A message. An optional `skill` field on the stage targets a specific skill ID.
- **Orchestrated mode**: The orchestrator agent **must be local** — it needs access to the ReAct loop, delegation tools, and system prompts that remote agents cannot provide. Individual stages can be remote.

### Swarms (Parties)

- **Circle (Round Robin)**: Remote agents participate as members. After turn 1, remote agents receive the last assistant message as context since they cannot read conversation history.
- **Chain (Relay)**: Remote agents **cannot** participate — relay mode requires the `__relay__` handoff tool which is injected into local agent system prompts. This is enforced when adding members.
- **Command (Directed)**: The coordinator agent **must be local** — it needs access to the coordinator system prompt and routing tools. Remote agents can be regular members.

### Conversations (Channels)

- Remote agents handle `input_required` responses — when a remote agent needs more information, its prompt is surfaced as an assistant message and the next user message continues the A2A task with the same `task_id` and `context_id`.

| Workflow | Remote as member/stage | Remote as orchestrator/coordinator |
|----------|----------------------|-----------------------------------|
| Pipeline (simple) | Yes | N/A |
| Pipeline (orchestrated) | Yes | No — must be local |
| Swarm (circle) | Yes | N/A |
| Swarm (chain) | No — enforced | N/A |
| Swarm (command) | Yes | No — must be local |

## Protocol Notes

- Summoner handles both Task and Message response types from `message/send` (the A2A spec allows either via `SendMessageResponse` oneof)
- Skill routing via `DataPart` is a convention, not part of the A2A wire protocol — skills are discovery-only on the agent card
- Streaming (`message/stream`) is not yet supported for outbound requests
